### Defect 1: launchd caps ExitTimeOut at 60s, so the compile-time guarantee is vacuous

### What is wrong

`crates/triaged/src/service.rs:176` sets `STOP_GRACE_SECS = 150`, and
`service.rs:179-183` asserts at compile time that it exceeds
`handover::SHUTDOWN_RESCUE_TIMEOUT` (90s, `handover.rs:237`). The assert's message
says a shorter grace period means "SIGKILL lands mid-handover and takes every live
session with it", and `handover.rs:234-236` documents the same invariant from the
other side.

macOS launchd does not honor 150. It silently substitutes 60 for any value above
60. Measured on this machine by loading a throwaway LaunchAgent at each value and
reading `launchctl print gui/$UID/<label> | grep 'exit timeout'`:

| plist `ExitTimeOut` | launchd reports |
| ------------------- | --------------- |
| 45                  | 45              |
| 59                  | 59              |
| 60                  | 60              |
| 61                  | 60              |
| 75                  | 60              |
| 150                 | 60              |
| 3000                | 60              |

Note it is not a clamp toward the request: anything over 60 is replaced by 60
outright. systemd's `TimeoutStopSec` has no such cap, so the two platforms cannot
keep sharing one constant.

So on macOS the real grace is 60s, while the three handover phases permit
10 + 60 + 10 = 80s (`HANDOVER_TRANSFER_TIMEOUT` at `handover.rs:164`,
`HANDOVER_ADOPTION_TIMEOUT` at `:179`, `HANDOVER_TEARDOWN_TIMEOUT` at `:214`).
The assert proves a relationship between two numbers, one of which the OS ignores.

### How much this actually matters

Less than it sounds, which is why it is worth fixing carefully rather than in a
panic. Phase 2 measures 10-15s in practice (session deserialize plus summarizer
model load), so the successor's adopt byte normally lands around 20s, leaving
roughly 40s of headroom. The single-session smoke test completed in about 1.5s.

The exposure is the tail: `HANDOVER_ADOPTION_TIMEOUT` was deliberately set to 60s
to tolerate a slow Phase 2, and a Phase 2 that actually uses its budget is now
guaranteed to outlive launchd's SIGKILL. The timeout tolerates exactly the case
the OS will kill.

### Recommended fix

Do not simply lower `STOP_GRACE_SECS` to 60 and call it done: the assert would
then fail to compile (60 > 90 is false), and forcing it to pass by shrinking
`SHUTDOWN_RESCUE_TIMEOUT` under 60 would cut the adoption budget that exists for
good measured reasons.

1. Platform-split the constant. macOS gets 60 (the real maximum, so the plist
   stops claiming something it does not get); systemd keeps 150.
2. Replace the single assert with one that states each platform's truth. On
   macOS the honest statement is *not* "the supervisor outlasts the rescue",
   because it cannot. It is "the rescue must survive its own SIGKILL", which is
   Defect 2.
3. Update the test at `service.rs:720`
   (`units_grant_the_session_rescue_time_to_finish`) which currently asserts the
   plist contains `<integer>150</integer>`, and record the cap in a comment there
   so nobody raises it again.

Defect 1 and Defect 2 are coupled: fixing the assert honestly requires deciding
what actually protects sessions when the grace period runs out. Do 2 first, or
do them together.

### Defect 2: a SIGKILL during Phase 2 loses every session

### The window

Once the successor writes `HANDOVER_ADOPT_BYTE` (`0x01`), a dead owner is already
handled correctly: `teardown_outcome` (`handover.rs:122`) maps
`Eof { peer_alive: false }` to `Adopt`, and the comment at `handover.rs:104-110`
explains why. The successor holds the only remaining handles, so refusing would
destroy sessions that are still fine. That reasoning is right and already covers
`launchctl kickstart -k`.

The gap is **after Phase 1 fd transfer but before the `0x01` write**, that is,
while the successor is doing its adoption work. `handover.rs:606-608` reasons
about a failure on that write:

> A failure on the 0x01 write itself is still fatal-by-`?`, and correctly so: a
> byte that never left means the outgoing daemon times out and keeps its
> sessions, so aborting here strands nothing.

That is true for an owner that aborted and kept serving. It is false for an owner
that was SIGKILLed: it does not keep its sessions, it has none, and its masters
died with it. The successor is then the only holder of the transferred
descriptors, and it aborts.

Confirmed failure path: `perform_handover_client` returns `Err`, and
`main.rs:317-323` logs "handover to existing daemon failed; starting fresh" and
breaks out of the loop, abandoning the transferred masters and cold-starting.

### Verify this before fixing it

The symptom depends on whether the received descriptors are owned or raw at the
point of the abort, and I did not confirm which:

- If they are wrapped in `OwnedFd` (or otherwise dropped), they close, the last
  reference to each master goes away, and the kernel SIGHUPs every child. Total
  loss.
- If they are still bare `RawFd`s, they leak, the masters stay open inside a
  process that has forgotten them, and the sessions are alive but orphaned with
  no reader. Recoverable only by a human noticing.

`recv_fds` in `handover.rs` returns raw descriptors and sets `FD_CLOEXEC` on
them by hand (macOS has no `MSG_CMSG_CLOEXEC`). Trace from there to the abort and
establish which it is. Both are bad; they need different words in the commit
message, and the leak variant may need a different fix.

### Recommended fix

Extend the reasoning that already exists one phase earlier. If the owner is gone
and this process is holding descriptors it received, the correct move is the same
one `teardown_outcome` already makes: adopt. Concretely, on a failed `0x01` write,
probe the peer with `peer_still_listening` (`handover.rs:554`, already written for
exactly this distinction) and:

- peer alive: abort as today. The owner kept its sessions and aborting strands
  nothing. This preserves the existing correctness argument unchanged.
- peer dead: adopt what was transferred rather than starting fresh.

This removes the dependence on the supervisor's grace period entirely, which is
the durable answer to Defect 1 and to any future OS that shortens the window
again.

### The danger to respect

The whole reason `TeardownOutcome::Refuse` exists is to prevent two processes
serving one session. Do not widen adopt-on-error into "adopt whenever anything
goes wrong". The liveness probe is what makes this safe, and a probe that returns
a wrong answer under load turns a session-loss bug into a double-owner bug, which
is worse and harder to see. Read the full contract at `handover.rs:93-134` before
touching it, and keep `peer_sends_commit` semantics intact.

### How to verify a fix

The unit suite cannot reach either defect. Use the two end-to-end scripts copied
to `<repo>/.local-verify/` (untracked, local only;
they were written in a session scratchpad that gets cleaned up):

- `rescue-smoke.sh`: starts an isolated daemon, creates a session, SIGTERMs the
  owner, and checks that the successor took over, that the owner exited, and that
  the session's child process is still alive.
- `rescue-skip.sh`: the four ways a stop must remain a real stop (no live
  sessions, `TRIAGE_NO_RESCUE=1`, the `DisableShutdownRescue` IPC call, and
  SIGINT behavior).

Both run against an isolated daemon with its own `HOME`, its own
`XDG_RUNTIME_DIR`, ports 17777/17778, and the summarizer off. Keep
`XDG_RUNTIME_DIR` short and under `/tmp`: a long path overruns `SUN_LEN` and the
socket bind fails in a way that looks like a daemon bug.

For Defect 2 specifically, the missing test is a SIGKILL of the owner during
Phase 2. A workable shape: start the successor, let it receive the fds, stop it
with `SIGSTOP` before its `0x01` write, `kill -9` the owner, then `SIGCONT` the
successor and assert the session's child survives. Consider whether this can be
made a Rust integration test rather than a shell script, since a shell script
outside CI will rot.

If you touch the supervisor units, re-measure the cap rather than trusting this
document, since it is one machine and one OS version:

```sh
launchctl print gui/$(id -u)/<label> | grep 'exit timeout'
```

### Local pitfalls that will cost you time

- `/opt/homebrew/bin` is not on `PATH` in these sessions, so `git` and `gh` hit
  the Git LFS hooks and abort. Prefix commands with
  `export PATH="/opt/homebrew/bin:$PATH"`.
- The triaged test suite is flaky in parallel (`session_context_*` fails roughly
  once per run). Use `--test-threads=1`. This is pre-existing, not caused by this
  branch.
- A bare `triaged` invocation attempts a handover against the live daemon.
  `--help` and `--version` are safe. Do not run the daemon binary casually while
  one is running.
- Installing a rebuilt binary: `rm` the old one first, then copy. Copying over it
  in place SIGKILLs the running process via a stale macOS signature cache.
- `cargo build --release` in the worktree also builds the Flutter bundle from the
  worktree's own `flutter/triage_client`, not the main checkout's. Put
  `<flutter-sdk>/bin` on `PATH` or the build script will
  fail or embed a stale bundle. `TRIAGE_SKIP_FLUTTER_BUILD=1` is fine for test
  runs and wrong for anything you intend to install.
- With the LaunchAgent installed, a manual `triaged --handover` runs twice,
  because launchd respawns the job it just tore down. Bootout the agent before
  any handover experiment.
